# 0006. 코드베이스 분석 기반 지침 생성을 구현하지 않는다

* **상태:** 채택됨 (Accepted)
* **일자:** 2026-09-14
* **결정자:** 제품 소유자·개발자
* **관련:** [ADR 0001](0001-product-scope.md)이 범위 밖에 둔 모델 호출·에이전트 런타임을 코드베이스 분석 기능에 적용한다. 외부 근거는 [`references.md`](../references.md#프로젝트-지침-자동-생성에-관한-근거)에 있다.

## 배경 (Context)

revfactory/harness 같은 도구가 프로젝트 코드베이스를 탐색한다는 점에서 "Agentic도 프로젝트를 분석해 지침을 작성해야 하는가"라는 질문이 나왔다.

- **harness의 실제 동작:** harness의 `SKILL.md` Phase 1은 "프로젝트 코드베이스 탐색 — 기술 스택, 데이터 모델, 주요 모듈 파악"을 수행한다. 하지만 그 결과는 에이전트 팀과 스킬 설계에만 쓴다. `CLAUDE.md`에는 트리거 포인터와 변경 이력만 기록하고 디렉터리 구조 같은 설명은 넣지 않는다고 명시한다. 따라서 harness는 프로젝트 지침을 작성하는 도구가 아니다.
- **이 저장소의 이력:** 같은 기능을 한 번 구현했다가 제거한 적이 있다. `41f5709`(2026-09-12)의 `detectProjectConstraints()`는 Next.js 라우터·Prisma·lockfile로 판단한 패키지 매니저를 감지해 `AGENTS.md`의 "프로젝트 기술 스택 및 핵심 제약 (자동 감지)" 절에 적었다. `2a3db65`(2026-09-13)의 제품 재구성에서 이 기능이 빠졌지만 제거 이유는 기록되지 않았다. 이 ADR이 그 공백을 채운다.

## 검토한 대안 (Options)

1. **파일 존재 여부로 스택을 감지하는 결정적 감지를 되살린다.** 모델 호출 없이 구현할 수 있다. 그러나 감지 결과는 대부분 에이전트가 `package.json`과 lockfile을 읽어 스스로 알아낼 수 있는 내용이며, 공식 가이드가 지침에서 빼라고 권하는 종류다. 프레임워크마다 감지 규칙을 계속 유지해야 하는 부담도 생긴다.
2. **LLM으로 코드베이스를 분석해 지침을 작성한다.** 모델 호출이 필요하므로 ADR 0001의 범위를 넘는다. Claude Code와 Codex가 기본으로 제공하는 `/init`과 기능이 겹친다.
3. **분석 기능을 두지 않는다.** 초안은 각 에이전트의 `/init`에 맡기고, Agentic은 그 결과가 동기화에서 보존되는 위치를 안내한다.

## 결정 (Decision)

3번을 채택한다. Agentic은 코드베이스를 분석해 프로젝트 지침을 작성하지 않는다.

프로젝트 지침에 무엇을 둘지에 대한 판단 기준도 함께 기록한다. 프로젝트 지침에는 **에이전트가 코드를 읽어 스스로 알아낼 수 없는** 명령·관례·결정·함정만 둔다. 디렉터리 구조, 파일별 설명, 의존성 목록, 저장소 개요는 두지 않는다. 빌드·테스트 명령이 `package.json`에 있더라도 에이전트가 추측하기 어려운 사용법이라면 넣을 수 있다. 근거는 다음 세 가지다.

- Anthropic best practices는 넣을 것으로 추측할 수 없는 Bash 명령, 기본값과 다른 코드 스타일, 프로젝트 고유의 아키텍처 결정, 흔한 함정을 든다. 뺄 것으로는 "코드를 읽으면 알 수 있는 모든 것"과 파일별 코드베이스 설명을 든다.
- Claude Code의 `/doctor`는 디렉터리 구조·의존성 목록·아키텍처 개요처럼 코드에서 도출할 수 있는 내용을 잘라내자고 제안한다.
- arXiv 2602.11988은 컨텍스트 파일이 과제 성공률을 일반적으로 높이지 못하고 추론 비용을 평균 20% 넘게 늘렸으며, 저장소 개요는 도움이 되지 않았다고 보고한다. 지침을 만드는 방식에 따라 결과가 달라진다는 반대 결과(arXiv 2606.20512)도 있다. 하지만 그 방식 역시 모델 호출로 지침을 만들기 때문에 이 결정을 바꾸지 않는다.

## 결과 및 영향 (Consequences)

- README와 제품 방향에 지원하지 않는 기능으로 이유와 함께 명시한다. 사용 가이드는 `/init` 초안을 `AGENTS.md`의 프로젝트 확장 영역에 두라고 안내한다. 여러 에이전트가 공통으로 읽는 표준은 `AGENTS.md`이기 때문이다. `CLAUDE.md`에 남긴다면 Agentic 관리 블록 밖에 두라고 안내한다.
- 이 안내가 실제 동작과 맞는지 2026-09-14에 임시 프로젝트로 재현했다. 환경은 Claude Code 2.1.270, codex-cli 0.154.0이며 모델 실행은 시나리오마다 1회다. Codex는 `codex exec`가 슬래시 명령을 받지 않으므로 TUI의 `/init`이 보내는 프롬프트 원문(`codex-rs/tui/assets/prompt_for_init_command.md`)을 그대로 전달했다.

  | 시나리오 | 관찰 | 이후 `profile sync` |
  | --- | --- | --- |
  | 적용된 프로젝트에서 Claude `/init`(사용자 설정 제외) | 관리 블록은 그대로 두고 블록 뒤에 `Commands`·`Architecture` 절을 추가했다 | `unchanged` |
  | 적용된 프로젝트에서 Claude `/init`(사용자 설정 포함) | 파일을 바꾸지 않고 초안을 출력한 뒤 둘 위치를 물었다 | `unchanged` |
  | 적용된 프로젝트에서 Codex `/init` 프롬프트 | "`AGENTS.md` already exists"라고 답하고 파일을 바꾸지 않았다 | `unchanged` |
  | Claude `/init` 후 `profile apply` | 생성된 27줄이 파일 위쪽에 그대로 남고 관리 블록이 뒤에 붙었다 | `unchanged` |
  | Codex `/init` 후 `profile apply` | 생성된 27줄이 모두 확장 영역 아래 `## Existing project guidance`로 옮겨졌다 | `unchanged`, 다른 프로필로 다시 apply해도 유지 |
  | 관리 블록 안 수정, 마커를 지운 재작성, `AGENTS.md` 프로필 영역 수정(모의 편집) | 모델 없이 직접 편집했다 | `Managed file changed outside Agentic`으로 중단하고 파일을 쓰지 않음 |
  | 관리 블록 밖 추가, `AGENTS.md` 확장 영역 추가(모의 편집) | 모델 없이 직접 편집했다 | 통과하고 추가 내용 유지 |

- **약한 곳:** 에이전트가 관리 영역을 피한 것은 모델의 판단이며 보장된 동작이 아니다. Claude는 `agentic.project.json`의 hash 기록을 읽고 스스로 블록을 피했다. Codex의 보호 장치는 프롬프트의 "do not overwrite or modify it" 한 문장뿐이다. 대화형 TUI의 `/init`은 `-p`·`exec` 실행과 다를 수 있지만 검증하지 않았다. Codex 실행에는 사용자 설정과 훅이 섞여 있었다. 만약 에이전트가 관리 영역을 고치더라도 Agentic은 동기화를 멈추고 파일을 쓰지 않으므로 사용자 내용은 잃지 않는다.
- **초안 품질:** 재현에서 Claude `/init`은 이 결정이 빼라고 권하는 저장소 개요(`Architecture`)를 넣었고, pnpm 저장소에 `npm test`를 적었다. 초안은 사람이 다듬어야 한다는 안내가 필요한 이유다.
- **재검토 조건:** 에이전트가 초안 생성 기능을 더 이상 제공하지 않거나, 코드에서 도출할 수 있는 개요가 과제 성공률을 높인다는 재현 가능한 근거가 나오면 이 결정을 다시 검토한다.
