# 0010. resolve --edit은 merge 결과에서 관리 영역 밖만 적용하고 관리 영역은 다시 만든다

* **상태:** 채택됨 (Accepted)
* **일자:** 2026-09-15
* **결정자:** 제품 소유자·개발자
* **근거:** 외부 근거 없음: 이 저장소에서 실제 VS Code로 `resolve --edit`을 실행해 관찰한 결과(배경 절)에 따른 결정이다.
* **관련:** [ADR 0008](0008-managed-conflict-recovery.md)이 정한 `--edit` 적용 조건("결과 파일의 관리 영역이 새로 만든 관리 영역과 같을 때만 적용")을 대체한다. ADR 0008의 나머지 결정은 그대로 둔다.

## 배경 (Context)

2026-09-15에 실제 VS Code(1.136.2)로 `profile resolve --edit`을 확인했다. 사용자는 아래쪽 Result 창에서 관리 블록 안의 줄을 `<!-- agentic:managed:end -->` 아래로 옮겨 저장했지만 결과가 거부됐다.

- 사용자 설정에 `"editor.formatOnSave": true`와 기본 포매터 `esbenp.prettier-vscode`가 켜져 있었다.
- 저장된 결과 파일은 관리 블록 안에 빈 줄이 늘고 글머리표 `*`가 `-`로 바뀌어 있었다. 옮긴 줄은 관리 블록 아래에 제대로 있었다.
- 사용자가 의도한 결과(줄만 옮긴 파일)를 로컬 Prettier 3.9.6으로 포맷하면 관리 블록 안의 변경이 같게 재현됐다.
- 같은 확인에서 Result 창이 Agentic이 새로 만든 내용으로 열려, 사용자가 위쪽 Current 창에서 변경을 먼저 받아들여야 옮길 줄이 나타났다. 결과 파일을 Agentic 쪽 내용으로 채웠기 때문이다. 터미널과 문서에는 이 절차가 안내되지 않았다.
- 결과 파일을 미리 채운 뒤 다시 확인하자, Result 창은 옮긴 줄이 들어간 상태로 열렸지만 VS Code가 `1 남은 충돌`을 표시하고 탭을 닫을 때 "파일에 처리되지 않은 충돌이 포함되어 있습니다" 경고를 띄웠다. `충돌과 함께 닫기`를 누르자 저장한 결과가 적용됐다. 이때 편집기에 넘긴 base와 Agentic 파일은 같았고 current만 한 줄이 더 있었다.
- 기존 규칙은 관리 영역이 한 글자라도 다르면 거부하므로 저장 시 포맷을 켠 편집기에서는 항상 실패한다. 자동 평가는 포매터가 없는 가짜 `code` 스크립트를 써서 이 문제를 잡지 못했다.

## 검토한 대안 (Options)

1. **거부를 유지하고 안내를 개선한다.** 거부될 때 VS Code의 "Save without Formatting"(Cmd+K S)이나 `formatOnSave` 끄기를 안내한다. 규칙은 단순하지만 포맷 설정을 쓰는 사용자는 매번 따로 저장해야 하고, 안내를 놓치면 계속 실패한다.
2. **공백·목록 기호 차이를 무시하고 비교한다.** 포매터마다 바꾸는 규칙이 달라 무시할 차이를 끝없이 늘려야 하고, 실제로 다른 내용을 같다고 판단할 위험이 있다.
3. **결과에서 관리 영역 밖만 가져오고 관리 영역은 다시 만든다.** 포매터가 관리 영역을 어떻게 바꾸든 결과가 같다. 관리 영역 안에 남긴 변경은 적용되지 않으므로 알려 줄 방법이 필요하다.

## 결정 (Decision)

3번을 채택한다.

- 결과 파일은 자동 해결(`resolve`)이 쓸 내용, 곧 관리 영역 안에서 추가·수정한 줄을 밖으로 옮긴 파일로 채워 편집기를 연다. 사용자는 위쪽 창에서 변경을 받아들이지 않고 Result 창을 확인·수정만 하면 된다. 편집기를 열기 전에 터미널에 확인 순서를 안내한다. 위쪽 `current-<파일>` 창의 강조 영역은 원래 고친 위치이므로 수락하지 않는다는 점, Result 창에서 남길 내용이 관리 영역 밖에 있는지 확인하고 저장한다는 점, 닫을 때 처리되지 않은 충돌 경고가 뜨면 Result 창을 다시 확인하고 `충돌과 함께 닫기`(Close with Conflicts)를 누른다는 점이다. 경고 자체를 없애도록 편집기 입력을 바꾸는 방법은 사용자가 원래 고친 위치를 current 창에서 볼 수 없게 되므로 택하지 않았다.
- 편집기를 닫으면 merge 결과 파일을 해당 파일의 새 내용으로 삼아 기존 계획 계산에 넘긴다. 포인터 파일은 관리 블록을, `AGENTS.md`는 확장 섹션 위 프로필 영역을 현재 프로필로 다시 만들고, 그 밖의 내용은 결과 파일 그대로 둔다.
- 결과의 관리 영역이 새로 만든 관리 영역과 다르면, 적용하지 않은 변경을 diff로 출력하고 merge 결과 파일을 지우지 않은 채 경로를 알린다. 같으면 임시 파일을 지운다.
- 결과 파일에 관리 마커가 없거나 `AGENTS.md`의 확장 섹션 제목이 없으면 멈춘다. 그대로 계획에 넘기면 관리 영역이 한 벌 더 생기거나 파일 전체가 기존 지침 영역으로 옮겨지기 때문이다.

## 결과 및 영향 (Consequences)

- 저장 시 포맷을 켠 VS Code에서도 `--edit`으로 충돌을 풀 수 있다.
- 편집하지 않고 저장·닫기만 하면 자동 해결과 같은 결과가 된다.
- 안내 문구는 VS Code의 버튼·경고 이름에 기댄다. 2026-09-15에 설치된 VS Code의 영어 문자열(`&&Close with Conflicts`, `The file contains unhandled conflicts.`)과 한국어 언어 팩 1.131의 문자열(`충돌과 함께 닫기(&&C)`, `파일에 처리되지 않은 충돌이 포함되어 있습니다.`)을 확인했다. VS Code가 이름을 바꾸면 안내도 고쳐야 한다.
- **약한 곳:** 사용자가 Result 창에서 관리 영역 안으로 되돌린 줄은 적용되지 않는다. `--edit`은 사용자가 저장한 결과를 따르기 때문이다. 대신 diff와 보존한 결과 파일로 되찾을 수 있다. 실제 VS Code가 결과 파일의 처음 내용을 Result 창에 그대로 보여 주는지는 2026-09-15 실행 확인으로만 검증했고 자동 평가는 가짜 `code`로 대신한다.
- 관리 영역 밖의 내용은 포매터가 바꾼 모양 그대로 저장된다(예: `- merge me`가 `* merge me`로 저장됨).
- 평가: `evals/conflict-resolve.test.mjs`가 포매터가 관리 블록을 바꾼 결과, 관리 영역 안에 변경을 남긴 결과, 마커를 지운 결과, 결과 파일을 건드리지 않고 닫은 경우(자동 해결과 같은 내용인지)를 가짜 `code` 모드로 고정한다.
