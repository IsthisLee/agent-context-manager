# 0016. 명령 등록부를 두고 종료 코드·JSON 출력·변경 확인 계약을 정한다

* **상태:** 채택됨 (Accepted)
* **일자:** 2026-09-15
* **결정자:** 제품 소유자
* **근거:** [CLI 계약과 지침 공급망 근거](../references.md#cli-계약과-지침-공급망-근거)
* **관련:** [ADR 0008](0008-managed-conflict-recovery.md)이 정한 충돌 종료 코드 1을 2로 바꾼다. [자연어 요청을 통한 agctx 사용](../discussion/architecture/topics/agent-mediated-usage.md)의 비대화형 계약을 구현한다.

## 배경 (Context)

스크립트·CI·에이전트가 agctx의 결과를 판단할 수단이 부족했다.

- 모든 실패가 종료 코드 1이었다. 관리 영역 충돌, 잘못 입력한 옵션, 내부 오류를 종료 코드로 구분할 수 없었고, 알 수 없는 명령은 도움말을 출력한 뒤 0으로 끝났다.
- 출력은 사람이 읽는 문장뿐이었다. 에이전트가 결과를 쓰려면 로케일에 따라 바뀌는 문장을 파싱해야 했다.
- 터미널이 아닌 환경에서도 `profile apply`·`sync`·`resolve`가 확인 없이 파일을 바꿨다. 에이전트가 계획을 보여 주지 않고 바로 실행해도 막을 장치가 없었다.
- 명령 목록이 명령 분기, 도움말, `src/commands/contracts.ts`, TUI 메뉴에 흩어져 있어 한 곳만 고치면 서로 어긋났다.
- 기능 인터페이스 동등성 규칙은 모든 사용자 기능에 CLI·TUI·프로필 관리 메뉴 세 경로를 요구했다. 이 규칙대로라면 CI에서 저장소를 검사하는 명령처럼 특정 프로필에 속하지 않는 기능에도 프로필 메뉴를 만들어야 한다.

## 검토한 대안 (Options)

| 항목 | 대안 | 판단 |
| --- | --- | --- |
| 종료 코드 | 0과 1만 쓴다 | 호출자가 충돌과 입력 오류를 구분하지 못한다 |
| | 도구 고유의 번호 체계를 새로 만든다 | 다른 CLI와 관례가 달라 호출자가 외울 것이 늘어난다 |
| | 결과 상태는 1–4로, 호출 실패는 BSD `sysexits`의 번호(64·69·70)로 나타낸다 | **채택.** 결과 상태와 호출 실패가 번호 대역으로 나뉜다 |
| 기계 판독 출력 | 명령마다 `--json` 형식을 따로 정한다 | 명령마다 필드 이름과 오류 표현이 달라진다 |
| | 모든 명령이 같은 결과 문서 형식을 쓴다 | **채택** |
| 변경 확인 | 확인하지 않는다 | 에이전트가 계획을 건너뛰고 바로 파일을 바꿀 수 있다 |
| | 터미널이 아니면 `--force`를 요구한다 | 이미 있는 `profile remove --yes`와 이름이 달라진다 |
| | 터미널이면 묻고, 아니면 `--yes`를 요구한다 | **채택.** 기존 `--yes` 관례와 같다 |
| 명령 목록 | 지금처럼 흩어 둔다 | 도움말·메뉴·평가가 서로 어긋난다 |
| | 등록부 한 곳에서 읽는다 | **채택** |

## 결정 (Decision)

1. **명령 등록부:** `src/commands/registry.ts`의 `COMMANDS`가 명령마다 id, 명령 단어, 위치 인자, 옵션, 돌려줄 수 있는 종료 코드, 표면(surface), 바꾸는 대상, TUI 항목, 프로필 관리 메뉴 항목을 정의한다. 전체 도움말, `<명령> --help`, 옵션 검사, 비슷한 명령 제안, 프로필 관리 메뉴, 동등성 평가가 모두 이 목록을 읽는다.
2. **종료 코드:**

   | 코드 | 뜻 |
   | --- | --- |
   | 0 | 성공 |
   | 1 | 뒤처짐: 프로젝트가 프로필의 새 버전을 반영하지 않았다 |
   | 2 | 관리 영역 충돌 |
   | 3 | 숨은 문자 |
   | 4 | 전달 누락: 에이전트가 지침을 읽지 않았다(이 코드를 돌려주는 명령은 아직 없다) |
   | 64 | 사용법 오류: 알 수 없는 명령·옵션, 인자 누락, 확인할 수 없는 환경 |
   | 69 | 외부 도구·네트워크·인증을 쓸 수 없다(`git`, VS Code CLI) |
   | 70 | 그 밖의 오류 |

   결과가 여러 개면 3 > 2 > 1 순서로 가장 심각한 코드를 돌려준다.
3. **출력:** `--json`을 주면 stdout에는 JSON 문서 하나만 쓰고 사람용 안내는 모두 stderr로 보낸다. 문서의 필드는 `schemaVersion`(현재 1), `command`, `exitCode`, `ok`, `data`, `warnings`, `errors[{ code, message, hint }]`다. 필드를 더하는 것은 호환되는 변경으로 보고, 필드를 빼거나 뜻을 바꿀 때 `schemaVersion`을 올린다.
4. **오류 문구:** 모든 오류는 `Error: <무엇이 잘못됐는지>`와 `Next: <바로 실행할 명령이나 조치>` 두 줄로 출력하고 로케일을 따른다. 알 수 없는 명령은 편집 거리가 가까운 명령을 제안하고 64로 끝낸다.
5. **확인과 질문:** 저장소 파일을 바꾸거나 원격으로 보내는 명령(`profile apply`·`sync`·`resolve`·`remove`·`push`)은 터미널에서 확인을 받는다. 터미널이 아니거나 `--json`이면 묻지 않고, `--yes`가 없으면 64로 멈추면서 `--dry-run`으로 계획을 먼저 보라고 안내한다. `--dry-run`은 확인 없이 실행한다. `--json` 실행은 TUI를 열지 않고 stdin에서 답을 읽지도 않는다. `profile create`·`setup`의 stdin 줄 입력은 `--json`이 없을 때만 유지한다.
6. **동등성 기준:** 표면이 `profile`인 명령(특정 프로필을 다루는 명령)은 CLI, TUI, `agctx profile list` 관리 메뉴 세 경로에서 실행할 수 있어야 한다. 표면이 `repository`인 명령(`check`처럼 저장소나 CI를 다루는 명령)과 `global` 명령(도움말·언어 설정)은 CLI만 필수다. `evals/interface-parity.test.ts`가 등록부를 기준으로 이 규칙을 검사한다.

## 결과 및 영향 (Consequences)

- **호환성 파괴:** 관리 영역 충돌의 종료 코드가 1에서 2로, 사용법 오류가 1에서 64로 바뀐다. 터미널이 아닌 환경에서 `profile apply`·`sync`·`resolve`는 `--yes`가 있어야 파일을 쓴다. 알 수 없는 명령은 0 대신 64로 끝난다.
- 에이전트와 CI는 문장을 파싱하지 않고 `--json` 문서와 종료 코드로 결과를 판단한다. 에이전트가 사용자에게 계획을 보여 주기 전에 `--yes`를 붙이지 않는다는 경계는 [자연어 요청을 통한 agctx 사용](../discussion/architecture/topics/agent-mediated-usage.md)에 둔다.
- 명령을 더하려면 등록부에 항목을 하나 추가하고 메시지 카탈로그에 `command.<id>.summary`를 영어·한국어로 넣는다. 빠뜨리면 `evals/messages.test.ts`가 실패한다.
- 평가: `evals/command-contract.test.ts`(종료 코드·JSON·`--yes`·`--help`·`check`), `evals/interface-parity.test.ts`(등록부 기준 동등성), `evals/messages.test.ts`(카탈로그 키).
- 한계: 종료 코드 4를 돌려주는 명령은 아직 없다. 명령별 `data` 필드는 아직 스키마 문서로 고정하지 않았고 평가가 주요 필드만 확인한다.
