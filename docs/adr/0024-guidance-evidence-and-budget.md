# 0024. 기본 지침 문장은 공식 문서·표준 근거가 있어야 하고 분량 예산 안에 머문다

* **상태:** 채택됨 (Accepted)
* **일자:** 2026-09-16
* **결정자:** 제품 소유자
* **근거:** [기본 지침 문장의 근거](../references.md#기본-지침-문장의-근거), [기본 지침의 근거와 분량에 관한 자료](../references.md#기본-지침의-근거와-분량에-관한-자료)
* **관련:** [ADR 0005](0005-guidance-level-semantics.md)의 "적용 수준마다 문구는 하나"는 그대로다. [ADR 0016](0016-command-contract.md)의 명령 계약을 따르며 `profile setup`의 옵션 이름 두 개를 바꾼다. 계약과 남은 작업은 [기본 지침의 근거 기준과 분량 예산](../discussion/architecture/topics/guidance-evidence-and-budget.md) 논의가 맡는다.

## 배경 (Context)

- `profile setup`이 만드는 지침은 이 패키지를 쓰는 모든 사용자에게 같은 문구로 배포되고, 사용자는 그 문구를 출발점으로 삼아 고쳐 쓴다. 출발점의 품질이 곧 많은 프로젝트 지침의 품질이 된다.
- 2026-09-14 감사에서 여섯 문장 가운데 TDD·변경 검토·보안에는 기록된 근거가 없었다. 문구도 "실제 결과를 보고한다"처럼 무엇을 보고할지 정하지 않아 행동을 바꾸기 어려웠다.
- 제품 소유자가 2026-09-16에 조건을 정했다. 최신 공식 문서나 기술 문서처럼 확실한 근거를 기반으로 하고, 근거에 없는 내용은 넣지 않는다.
- 근거를 늘리면 분량이 늘어난다. 공식 문서는 지침이 길어지면 규칙이 묻힌다고 경고하고, Claude Code는 파일마다 200줄 미만을 목표로, Codex는 합산 32 KiB를 한도로 제시한다.

## 검토한 대안 (Options)

| 대안 | 판단 |
| --- | --- |
| 근거 없이 모범 사례로 보이는 문장을 유지한다 | 사용자가 어느 문장을 믿고 어느 문장을 고칠지 판단할 수 없다 |
| 공식 문서·표준만 단독 근거로 인정하고, 연구는 보조로 쓴다 | **채택.** 이 분야 연구는 결과가 엇갈려 단독 근거로 쓰기 어렵다 |
| 연구 논문도 단독 근거로 인정한다 | 채택하지 않는다. 좁은 조건의 결과가 넓은 결과를 이길 수 있다 |
| 분량 상한을 두지 않는다 | 근거가 늘수록 문구가 길어지고, 공식 문서가 경고한 대로 규칙이 묻힌다 |

## 결정 (Decision)

### 채택 조건

배포 문장은 네 질문을 모두 통과해야 한다.

1. 이 문장을 지우면 에이전트가 실수하는가.
2. 지켰는지 확인할 수 있을 만큼 구체적인가.
3. 특정 언어·프레임워크·프로젝트에 매이지 않는가.
4. 아래 등급의 근거가 있는가.

### 근거 등급

| 등급 | 종류 | 쓰는 방식 |
| --- | --- | --- |
| A | 에이전트 제공사의 공식 문서와 공식 엔지니어링 글, 표준 기관의 기술 문서(OWASP 등) | 단독 근거로 채택할 수 있다 |
| 보조 | 측정 방법과 결과를 공개한 연구, 실무자 글, 다른 도구의 규칙 | 단독 근거로 쓰지 않는다. A 등급 문장을 보강하거나 이름의 출처를 밝히는 데만 쓴다 |

- 근거가 엇갈리면 양쪽이 모두 지지하는 부분만 문장에 반영하고, 엇갈린 결과를 `references.md`에 함께 적는다. 어느 한쪽을 골라야 하면 지금 지원하는 에이전트와 조건이 가깝고 범위가 넓은 근거를 먼저 보고, 조건이 비슷할 때만 더 최신 근거를 앞에 둔다.
- 근거를 인용할 때는 원문을 그대로 적고 한국어 번역과 확인일을 붙인다. 문구를 고칠 때는 인용한 문서를 다시 열어 확인일을 새로 적는다.
- 에이전트 시스템을 만드는 사람을 위한 글의 원칙을 에이전트 자신의 작업 규칙으로 옮겨 쓸 때는 그 사실을 `references.md`에 밝힌다.
- 근거를 찾지 못한 문장은 버리지 않고 보류한다. 필요한 사용자는 프로필 `AGENTS.md`에 직접 쓴다.

### 추적과 검사

- 지침 카탈로그는 항목마다 근거 열을 두고 `references.md`의 해당 절로 링크한다. 근거 링크가 없는 행이 있으면 `pnpm run check`의 `check:docs`가 실패한다.
- 모든 항목을 `strict`로 켠 프로필 `AGENTS.md`의 guidance 블록은 100줄·8 KiB 이하다. 평가가 ko·en 모두를 검사한다. Claude Code가 권하는 200줄의 절반이고 Codex 한도의 4분의 1이라, 나머지 공간은 사용자와 프로젝트 지침에 남는다.

### 항목 이름과 옵션

- `--harness`를 `--workflow`로, `--documentation`을 `--instructions`로 바꾼다. 표시 이름도 "작업 흐름"과 "지침 파일"로 바꾼다. 옛 옵션 이름은 남기지 않는다.
- 이유는 두 가지다. 하네스는 공식 문서에서 에이전트를 돌리는 프로그램과 그 설정을 가리키는데 이 항목은 에이전트의 작업 흐름을 다룬다. 문서화 항목은 내용이 프로젝트 문서 갱신에서 에이전트 지침 파일 관리로 바뀌었다.

## 결과 및 영향 (Consequences)

- **호환성 파괴:** `agctx profile setup --harness`·`--documentation`을 쓰던 스크립트는 사용법 오류(64)로 멈춘다. 기존 프로필에 저장된 `harness`·`documentation` 설정 값은 읽지 않으므로, 두 항목은 다시 고르기 전까지 기본값 `recommended`로 생성된다.
- 문구가 바뀌어도 기존 프로필은 자동으로 바뀌지 않는다. `profile setup`을 다시 실행하면 guidance 블록이 바뀌고 `profile sync`로 프로젝트에 반영된다. 블록 밖에 쓴 내용은 그대로 남는다.
- 문구를 고칠 때는 [지침 카탈로그](../contributing/guidance-catalog.md), `src/i18n/index.ts`, `references.md`를 같은 변경에서 고친다.
- 문장이 실제로 에이전트의 실수를 줄이는지는 모델을 실행해야 알 수 있어 자동 평가에 넣지 않는다. 문구를 바꿀 때 유지관리자가 같은 과제를 전후 문구로 실행해 비교하고 결과를 논의 문서에 남긴다.
