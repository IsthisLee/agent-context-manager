# 0034. AGENTS.md의 관리 영역 경계를 마커로 표시한다

* **상태:** 채택됨 (Accepted)
* **일자:** 2026-09-20
* **결정자:** 제품 소유자
* **근거:** [포매터가 관리 영역을 바꾸는 범위](../references.md#포매터가-관리-영역을-바꾸는-범위)
* **관련:** [ADR 0008](0008-managed-conflict-recovery.md)이 정한 충돌 복구 절차와 [ADR 0010](0010-edit-merge-regenerates-managed-area.md)의 편집 병합 계약은 그대로 두고, 경계를 찾는 방법만 바꾼다.

## 배경 (Context)

- 포인터 파일(`CLAUDE.md`, `.agents/rules/agctx.md`)은 `<!-- agctx:managed:start -->`와 `<!-- agctx:managed:end -->` 사이가 관리 영역이라고 파일에 적어 둔다. 프로젝트 `AGENTS.md`만 표지가 없고, 확장 섹션 제목(`## 4. 프로젝트 규칙 확장 (SSOT)`)의 생김새를 정규식으로 알아맞혀 경계를 정했다. 그렇게 정한 ADR은 없다.
- **제목을 알아맞히는 방식은 빗나간다.** 번호·점·제목 단계가 달라지면 경계를 잃어 파일 전체가 관리 영역이 됐고, 사용자가 쓴 규칙까지 충돌로 판정했다. 2026-09-20에 정규식을 넓혀 그 증상을 막았지만 구조는 그대로였다.
- **제목이 경계라서 제목을 바꿀 수 없었다.** 제목을 `## 우리 팀 규칙`으로 바꾸자 `agctx check`가 `conflict`와 종료 코드 2로 멈췄다(2026-09-20 실측). 사용자의 파일인데 제목 한 줄을 자기 말로 바꿀 수 없었다.
- **보이는 표지가 엉뚱한 곳을 가리켰다.** 프로필 `AGENTS.md`의 `<!-- agctx:guidance:start/end -->`가 프로젝트로 그대로 복사됐다. 이 표지는 `profile setup`이 다시 쓰는 범위를 뜻할 뿐 프로젝트에서는 아무 의미가 없는데, 관리 영역 안에서 끝나는 것처럼 보였다. 실제 관리 영역은 그 아래로 여섯 줄 더 이어졌다.
- 경계 아래 안내 한 줄까지 프로필이 소유했으므로, 그 문장을 지우면 `sync`가 되살렸다.

## 검토한 대안 (Options)

| 대안 | 판정 |
| --- | --- |
| 제목 정규식을 계속 넓힌다 | 채택하지 않는다. 사용자가 쓸 수 있는 제목을 미리 다 알 수 없고, 빗나가면 사용자 규칙이 통째로 남의 영역이 된다 |
| 경계를 보여 주는 명령을 더한다 | 채택하지 않는다. 파일을 열었을 때는 여전히 보이지 않고, 명령을 아는 사람에게만 도움이 된다 |
| 제목 위에 안내 주석만 넣는다 | 채택하지 않는다. 보이기는 하지만 판정에 쓰이지 않아, 지워도 아무 일이 없는 장식이 하나 더 생긴다 |
| **`<!-- agctx:managed:end -->`를 둔다** | **채택.** 포인터 파일과 같은 표지이고, 경계가 파일에 적히므로 알아맞힐 것이 없다 |

`start` 표지는 두지 않는다. 프로젝트 `AGENTS.md`는 파일 첫 줄부터 관리 영역이라 시작을 적을 곳이 없고, 표지를 하나 더 두면 사용자가 쓸 수 있는 자리가 위아래로 갈린다.

## 결정 (Decision)

- 프로젝트 `AGENTS.md`의 관리 영역은 **파일 처음부터 `<!-- agctx:managed:end -->`까지**다. 마커 자체도 관리 영역에 들어가므로 지우면 감지된다.
- 마커 아래는 전부 사용자 것이다. 확장 섹션 제목과 그 아래 안내 한 줄도 사용자 것이 되므로, 바꾸거나 지워도 `sync`가 되돌리지 않는다. 처음 적용할 때 쓸 자리를 알려 주려고 한 번 써 줄 뿐이다.
- 마커가 없는 파일은 지금까지처럼 확장 섹션 제목으로 경계를 찾는다. 이 경로는 마이그레이션 전용이며, `profile sync` 한 번이면 마커가 들어간다.
- 프로젝트 `AGENTS.md`를 만들 때 프로필 본문의 `<!-- agctx:guidance:start/end -->` 두 줄을 뺀다. 그 사이의 지침 본문은 그대로 둔다.
- 관리 영역이 마지막으로 쓴 원문과 **표현만** 다르면 사람이 고친 것으로 보지 않는다. 목록 기호, 줄 끝 공백, 블록 사이의 빈 줄, 줄 끝 문자, 문단 안의 줄바꿈이 대상이고 낱말은 건드리지 않는다. 문단 안의 단일 줄바꿈은 Markdown에서 공백과 같으므로 한 줄로 합쳐 비교하며, 줄바꿈에 뜻이 있는 코드 블록은 그대로 둔다. 기준이 되는 원문은 `.agctx/base/`에 있으므로, 원문을 알 수 없으면 지금까지처럼 해시만 비교한다.

## 결과 및 영향 (Consequences)

- 파일을 열면 경계가 보인다. 무엇이 agctx 것이고 무엇이 내 것인지 문서를 찾아보지 않아도 된다.
- 확장 섹션의 제목을 자기 말로 바꾸고 안내 한 줄을 지워도 `agctx check`가 통과한다(2026-09-20 실측, 종료 코드 0).
- 기존 저장소는 `profile sync` 한 번으로 옮겨 간다. 제보된 프로젝트의 사본에서 마커가 들어가고 프로필용 표지가 빠지며 사용자 규칙이 그대로 남는 것을 확인했다(2026-09-20 실측).
- 마커를 지우면 제목 탐지로 되돌아가고, 제목도 없으면 파일 전체가 관리 영역이 되어 충돌한다. 마커를 지우기 전과 같은 상태이므로 더 나빠지지는 않는다.
- 표현 차이를 사람의 편집으로 보지 않게 되면서, 편집기가 저장할 때 관리 영역을 다시 포맷해도 충돌이 나지 않는다. 문단을 정해진 너비로 다시 접는 설정(`proseWrap: always`)까지 포함한다. 적용한 프로젝트를 그 설정으로 포맷한 뒤 `agctx check`가 `behind`(1)로 끝나 `profile sync` 한 번에 풀렸고, 같은 파일에서 낱말 하나를 바꾸자 `conflict`(2)로 멈췄다(2026-09-21 실측).
