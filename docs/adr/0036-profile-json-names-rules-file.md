# 0036. profile.json이 프로필의 규칙 파일을 가리킨다

* **상태:** 채택됨 (Accepted)
* **일자:** 2026-09-21
* **결정자:** 제품 소유자
* **근거:** 외부 근거 없음: agctx 자신의 파일 형식과 옛 릴리스의 동작만 다루며, 판단 근거는 논의 문서의 실측 출력이다.
* **관련:** [기존 Git 저장소를 프로필 원천으로 쓰기](../discussion/architecture/topics/existing-repository-source.md)의 제안을 구현한다. [ADR 0017](0017-git-profile-sharing.md)의 "저장소 하나에 프로필 하나"와 "`profile.json`의 이름을 쓴다"는 그대로 두고, 규칙 파일이 루트의 `AGENTS.md`여야 한다는 전제만 바꾼다.

## 배경 (Context)

- `profile clone`은 원격 저장소 루트의 `profile.json`과 `AGENTS.md`만 받았다. 조직은 대개 규칙 저장소를 agctx보다 먼저 갖고 있고, 그 저장소는 규칙 파일을 정책 문서·CI 워크플로와 함께 하위 폴더에 둔다. 실제 조직 저장소를 받으려다 64로 거부당했다.
- 우회가 막혀 있었다. 루트 `AGENTS.md`를 하위 파일로 가는 심볼릭 링크로 두면 거부했고, 거부 안내대로 새 프로필을 만들어 그 저장소에 `connect`하면 이력이 갈라져 `push`와 `pull`이 모두 2로 멈췄다. 되는 길은 규칙 파일을 루트로 옮기는 것뿐이었다.
- `profile.json`은 원천이 가져야 한다. ADR 0017은 받는 쪽이 이름을 정하는 대안을 팀원마다 이름이 달라진다는 이유로 버렸다.

## 검토한 대안 (Options)

| 항목 | 대안 | 판단 |
| --- | --- | --- |
| 규칙 파일 위치 | 지금처럼 루트 `AGENTS.md`만 받는다 | 원천 저장소의 구조를 agctx에 맞춰 바꾸게 하고, 옮긴 파일이 그 저장소 자신의 규칙으로도 읽힌다 |
| | `profile clone --path <폴더>`로 하위 폴더를 받는다 | 받는 사람마다 옵션을 맞춰야 하고 경로를 원천이 정하지 못한다 |
| | 심볼릭 링크를 허용한다 | 저장소 밖 파일을 프로필로 읽을 수 있다 |
| | `profile.json`의 필드가 규칙 파일을 가리킨다 | **채택.** 원천이 이름과 경로를 함께 소유한다 |
| 필드 이름 | `agentsFile` | 제품 저장소에 만들어지는 `AGENTS.md`와 혼동하기 쉽다 |
| | `instructions` | **채택.** 코드의 `instructionsPath`와 같은 이름이다 |
| 스키마 버전 | `schemaVersion` 1에 선택 필드로 더한다 | 옛 agctx가 필드를 무시하고 루트의 다른 `AGENTS.md`를 경고 없이 적용하는 것을 실측했다 |
| | `instructions`가 있으면 2를 요구한다 | **채택.** 0.4.0까지의 모든 릴리스는 `schemaVersion` 1만 받으므로 이 프로필을 거부한다 |
| 확장자 | 제한하지 않는다 | 잘못된 파일을 가리켜도 제품 저장소에 들어간 뒤에야 드러난다 |
| | `.md`만 받는다 | **채택.** 한 번 허용한 뒤 조이면 호환성이 깨지므로 좁게 시작한다 |

## 결정 (Decision)

1. **필드:** `profile.json`의 `instructions`가 프로필 폴더 안의 규칙 파일을 가리킨다. 없으면 루트의 `AGENTS.md`다. 새 명령이나 옵션은 없고, 필드는 원천 저장소에서 사람이 쓴다. `profile create`는 지금처럼 `instructions` 없이 루트 `AGENTS.md`를 만든다.
2. **스키마 버전:** `instructions`가 있으면 `schemaVersion` 2여야 한다. 1에 `instructions`가 있으면 거부한다. `instructions`가 없는 1과 2는 모두 받는다.
3. **경로:** 저장소 루트를 기준으로 한 상대 경로이고 폴더는 `/`로 나눈다. `.md` 파일만 가리킬 수 있다. 빈 값, 절대 경로, 역슬래시, `.`·`..` 조각, `.git` 조각은 거부한다. 판정은 `src/profile/store.ts`의 `isInstructionsPath`가 한다.
4. **원격에서 받는 파일:** `clone`은 임시 폴더에서, `pull`은 들어올 커밋에서 `profile.json`을 먼저 읽어 경로를 정하고, 그 파일이 일반 파일인지와 숨은 문자가 없는지 검사한다. 파일이나 거쳐 가는 폴더가 심볼릭 링크면 거부한다. `pull`은 경로를 바꾸는 커밋도 받는다.
5. **보관함의 프로필:** `readProfile`이 경로를 정하고 `apply`·`sync`·`setup`·`profile view`·TUI가 따른다. `setup`은 가리킨 파일에 지침 구역을 쓴다. 보관함은 사용자의 폴더이므로, 이미 있는 로컬 프로필의 규칙 파일은 링크여도 읽는다.
6. **고정한 프로젝트:** 기록한 커밋의 `profile.json`에서 경로를 읽어 그 커밋의 파일로 다시 만든다. 커밋하지 않은 수정은 `profile.json`과 가리킨 파일을 보고 판정한다.
7. **거부 안내:** `profile.json`이 없는 저장소를 거부할 때 최소 예시와 `instructions`를 보여 준다.

## 결과 및 영향 (Consequences)

- 기존 규칙 저장소는 `profile.json` 하나만 더하면 받을 수 있다. 규칙 파일을 옮기거나 README를 고치지 않아도 된다.
- `instructions`가 없는 기존 프로필과 `profile create`로 만든 프로필은 아무것도 바뀌지 않는다.
- `instructions`를 쓴 프로필은 0.4.0 이하에서 `profile.json이 올바른 프로필 메타데이터가 아닙니다`로 거부된다. 팀원 모두가 이 기능이 든 버전 이상을 써야 한다.
- 평가: `evals/profile-instructions.test.ts`(clone·apply·setup·pull·고정 복원·수정 판정·거부 경로 19개). 거부 평가는 검사를 하나씩 빼 보는 변이로 실패하는지 확인했다.
- 한계:
  - 절대 경로와 `.git` 조각 검사는 다른 방어선 뒤에 있다. 경로를 붙이는 방식과 Git 자체가 이미 막으므로, 이 검사만 빼서는 평가가 실패하지 않는다.
  - 저장소 하나에 프로필 하나만 받는다. 규칙 파일 하나만 프로필에 들어간다.
  - 고정한 커밋의 규칙 파일이 그 커밋에서 심볼릭 링크였다면 다시 만들지 못하고 69로 멈춘다. 이전에는 링크 대상 경로 문자열을 규칙 내용으로 썼다.
