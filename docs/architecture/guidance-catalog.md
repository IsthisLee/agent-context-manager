## 지침이 만들어지는 두 경로

프로필의 `AGENTS.md`에 지침이 들어가는 길은 두 가지다.

1. **`profile setup`이 관리하는 블록.** `setup`은 아래 6개 항목을 골라 `<!-- agentic:guidance:start --> … <!-- agentic:guidance:end -->` 블록으로 프로필 `AGENTS.md`에 쓴다. 이 블록은 `setup`을 다시 돌릴 때 통째로 교체된다.
2. **사용자가 직접 편집.** 프로필의 `AGENTS.md`는 일반 텍스트 파일이다. 관리 블록 **바깥**에 원하는 지침을 직접 써도 된다. `setup`은 블록 안만 교체하므로 바깥 내용은 보존되고 `profile apply`로 적용할 때 프로필 `AGENTS.md` 전체가 프로젝트로 전달된다.

`setup`은 시작점이다. 6개 항목은 자주 쓰는 기본 뼈대를 빠르게 켜는 용도이고 팀·프로젝트에 필요한 두터운 지침은 프로필 `AGENTS.md`를 직접 편집해 채운다. 두 경로가 한 파일에서 공존한다.

## 지침 항목 6개

아래는 현재 배포되는 항목과 문구다. 문구는 `recommended`·`strict`에서 같고, `off`면 항목 자체가 산출물에서 빠진다.

| 항목 | 목적 | 배포 문구 |
| --- | --- | --- |
| 하네스 동작 | 작업을 계획하고 실제 검증 결과를 보고하는 기본 작업 방식 | 작업을 작은 단위로 계획하고, 변경 후 프로젝트의 검증 명령을 실행해 실제 결과를 보고한다. |
| TDD | 실패 테스트부터 시작하는 Red-Green-Refactor 개발 방식 | strict이면 Red-Green-Refactor를 따르고, recommended이면 가능한 경우 실패 테스트부터 작성한다. |
| 리뷰 | 변경 범위와 위험을 확인하는 리뷰 방식 | 변경 범위와 위험을 검토하고, 설정된 경우 독립적인 리뷰 결과를 남긴다. |
| 검증 | 프로젝트의 검증 명령을 실행하고 결과를 기록하는 방식 | 프로젝트가 선택한 검증 명령을 실행한다. 실행 결과는 실행 사실이며 품질 전체의 증명이 아님을 명시한다. |
| 문서화 | 계약·정책·구조 변경을 정본 문서에 반영하는 방식 | 사용자에게 영향을 주는 계약·정책·구조 변경은 관련 정본 문서와 함께 갱신한다. |
| 보안 | 비밀값 보호와 외부 변경 승인에 관한 규칙 | 비밀값을 출력·커밋하지 않고, 외부 변경과 권한이 필요한 작업은 사용자 승인을 받는다. |

기본값은 모든 항목이 `recommended`다. 항목 선택 계약과 재실행 정책은 [setup과 지침 옵션](../discussion/architecture/topics/setup-and-guidance.md)에서 관리한다.

## 적용 수준 (off / recommended / strict)

- `off` — 이 항목을 프로필 지침에서 뺀다.
- `recommended` — 기본값으로 포함한다.
- `strict` — 포함한다.

현재 동작에는 한 가지 공백이 있다. `recommended`와 `strict`는 산출물에서 `적용 수준:` 라벨 한 줄만 다르고, 그 아래 규칙 문구는 같다. 두 수준이 각각 무엇을 다르게 요구하는지의 정의가 산출물·템플릿 어디에도 없다. 이 공백의 해소 방안은 [지침 적용 수준의 의미 정의](../discussion/architecture/topics/guidance-level-semantics.md)에서 관리한다.

## 알려진 공백과 개선 방향

이 카탈로그가 지금 사실대로 담고 있는 약점이다.

1. **하네스 문구가 근거를 다 반영하지 못한다.** [references.md](../references.md)의 하네스 연구는 "복잡한 하네스는 비용·지연을 키우므로 기본은 작게 유지하고 선택적으로 확장한다"를 원칙으로 둔다. 그런데 배포 문구는 계획·보고 습관만 담고 이 원칙을 문장으로 내리지 못했다.
2. **레벨이 라벨만 다르다.** 위의 적용 수준 항목에서 짚은 그대로다.
3. **각 항목이 한 문장으로 얇다.** 배포 배관은 있고 실제 지침 내용의 깊이는 부족하다.

개선은 **근거 기반 심화 + 항목 6개 유지** 방향으로 진행한다. 각 항목을 references 근거로 두텁게 쓰고 `recommended`와 `strict`가 요구하는 행동을 실제로 차등화한다. 항목 수는 늘리지 않는다. 이 방향이 확정되면 관련 문구를 `bin/i18n.mjs`와 이 문서에 함께 반영하고 필요한 경우 ADR로 근거를 남긴다.
