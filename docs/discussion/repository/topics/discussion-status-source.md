## 현재 동작

주제 하나의 상태가 바뀌면 사람이 세 곳을 고친다.

```text
주제 문서의 **상태:** 줄  ──┐
영역 색인 표의 상태 칸     ──┼── 같은 값을 손으로 세 번 쓴다
README의 구현됨·구현 중·제안 단계 목록 ──┘
```

`check:docs`는 앞의 두 곳이 같은지 검사하고(`tools/check-docs.ts:164`), 구현된 주제에 구현 기록이 있는지 검사한다(`tools/check-docs.ts:148`). README 목록은 검사하지 않는다.

## 제안 동작

1. **정본 한 파일.** 논의 영역마다 주제의 파일 이름, 제목, 상태, 중요도, 선행 단계, 핵심 결과를 JSON 한 파일에 둔다.
2. **생성.** 영역 색인 표와 README 상태 목록은 JSON에서 생성한다. CLI 레퍼런스를 명령 등록부에서 생성하는 방식과 같다. 생성 결과가 커밋된 파일과 다르면 `check`가 실패한다.
3. **정합성 검사.** 구현 기록이 있는 주제인데 JSON 상태가 `Implemented`가 아니면 실패한다. JSON에 있는데 파일이 없거나, 파일이 있는데 JSON에 없어도 실패한다.

## 검토한 대안

| 대안 | 내용 | 판단 |
| --- | --- | --- |

| 색인 하나에만 | 주제 문서의 상태 줄을 없애고 색인 표에만 쓴다. | 채택하지 않는다. 생성기가 필요 없지만 README 목록은 여전히 손으로 맞춰야 하고, Markdown 표는 기계가 검사하기 어렵다. |
| 지금 유지 | 세 곳에 쓰는 방식을 유지한다. | 채택하지 않는다. 유지 비용과 README 핀의 헛걸림이 남는다. |

## 결정

2026-09-19, 제품 소유자.

- 상태의 정본은 JSON 한 파일이다. 한 파일만 읽으면 모든 주제의 상태를 알 수 있고, 생성기는 JSON을 읽기만 하면 된다.
- 에이전트가 Markdown보다 JSON을 덜 함부로 고친다는 외부 근거가 있다([세션 사이 작업 상태 근거](../../../references.md#세션-사이-작업-상태-근거)).
- 주제 문서를 고치면서 다른 파일의 상태를 바꾸는 것을 잊기 쉽다는 약점은 [제안 동작](#제안-동작) 3번의 검사로 막는다.

구현하기 전에 남은 세 항목도 2026-09-19에 제품 소유자가 정했다.

- JSON은 저장소에 한 파일(`docs/discussion/topics.json`)로 둔다. 위의 "한 파일만 읽으면 모든 주제의 상태를 알 수 있다"는 근거와 맞는 쪽이다.
- 주제 문서의 상태 줄은 없애지 않고 JSON에서 생성해 남긴다. 링크로 주제 문서만 연 사람도 상태를 볼 수 있다.
- README 상태 목록은 주제 이름만 생성한다. 구현 중 항목 뒤에 붙던 괄호 설명은 없애고, 자세한 내용은 색인에서 본다.

## 결정·검증 항목

- **JSON 위치와 이름:** 영역마다 하나를 둘지, 저장소에 하나를 둘지. 저장소에 하나로 정했다([결정](#결정)).
- **주제 문서의 상태 줄:** 없앨지, JSON에서 생성해 남길지. 생성해 남기기로 정했다.
- **README 상태 목록:** 생성할지, README에서 논의 색인 링크만 둘지. 이름만 생성하기로 정했다.
- **검증:** 생성기를 넣은 뒤 상태를 바꾸는 변경에서 사람이 고친 파일 수를 센다. 결과는 [구현 기록](#구현-기록-상태-json과-생성기)의 평가 항목에 있다.

**2026-09-19.**

* **결정:** [결정](#결정) 절의 세 항목대로 구현했다. 생성 대상과 `check:docs`가 하는 검사의 정본은 [문서 게이트의 생성하는 논의 상태](../../../contributing/doc-gate.md#생성하는-논의-상태)다.
* **구현:** `tools/discussion-topics.ts`가 `docs/discussion/topics.json`을 읽고, `tools/generate-discussion-status.ts`가 주제 문서의 상태 줄, 영역 색인 표, 아키텍처 색인의 단계 그림 색, 두 README의 목록을 생성한다. `check:docs`는 주제 문서의 상태 줄 대신 `topics.json`을 읽고, 주제 문서의 제안 요약에 남은 `중요도`의 첫 단어가 `topics.json`의 `importance`와 같은지 대조한다. 두 README에서 논의 폴더 핀을 뺐고, 핀한 문서를 해시할 때 생성 블록의 내용을 뺀다(`withoutGeneratedBlocks`). `AGENTS.md`의 구현 기록 규칙, [구현 계약](../../architecture/topics/implementation-contracts.md#구현-기록), `repo-docs` 스킬 4단계, 두 색인의 안내를 같은 변경에서 고쳤다.
* **평가:** `evals/discussion-status.test.ts`의 6개 평가가 생성 결과가 최신인지, 상태 하나를 바꾸면 주제 문서·아키텍처 색인·두 README가 함께 바뀌는지, 구현 기록이 있는 주제가 `Proposed`로 남으면 막히는지, 요약표의 중요도가 `topics.json`과 같은지, 생성 블록이 해시에서 빠지는지 검사한다. 직접 실험으로 `topics.json`에서 `apply-selection.md`의 상태 하나만 바꾸고 생성했더니, 사람이 고친 파일은 1개, 생성기가 고친 파일은 4개였고, 다시 stamp하지 않아도 `node tools/check-docs.ts`가 종료 코드 0으로 끝났다. 전에는 아키텍처 주제 하나의 상태를 네 파일 다섯 곳에 손으로 썼고, 주제 문서를 고치면 두 README가 해시 게이트에 걸렸다.
* **계획과 달라진 점:**
  - [제안 동작](#제안-동작) 3번은 "구현 기록이 있는데 `Implemented`가 아니면 실패"였다. 그러나 `Implementing` 주제도 구현 기록을 쌓는다(`agent-mediated-usage.md` 3개, `managed-artifact-safety.md` 2개). 그래서 "구현 기록이 있는데 `Proposed`면 실패"로 구현했다.
  - [현재 동작](#현재-동작)은 상태를 세 곳에 쓴다고 적었지만 실제로는 다섯 곳이었다. 아키텍처 색인의 단계 그림과 영어 README가 더 있었고, 둘 다 생성 대상에 넣었다. 처음 생성하자 12단계가 표에서는 `Implementing`인데 그림에서는 회색(`Proposed`)이던 불일치가 고쳐졌다.
  - 두 README가 서로를 핀하므로 목록만 다시 생성해도 상대 README가 해시 게이트에 걸렸다. 상태 변경이 다시 stamp를 요구하지 않도록 핀한 문서의 생성 블록을 해시에서 뺐다.
