## 현재 동작

코드 동작을 서술하는 문서는 상단 마커 두 줄로 인용한 소스를 핀한다. `pnpm run check`의 `check:docs`가 그 소스를 다시 해싱해 기록값과 비교하고, 다르면 실패한다. 사람이 문서를 다시 읽고 고친 뒤 `node tools/check-docs.ts --stamp`로 해시를 다시 기록한다. 계약의 정본은 [문서 게이트](../../../contributing/doc-gate.md)다.

## 측정

2026-09-18에 이 저장소에서 잰 값이다.

- **검사 시간:** `node tools/check-docs.ts` 세 번 실행에 0.21초·0.25초·0.32초. 핀된 문서 29개에 대해 파일 해시를 393번 계산한다. 계산 비용은 문제가 아니다.
- **소스 하나를 고쳤을 때 실패하는 문서 수:** 최소 4, 중앙값 6, 상위 10% 9, 최대 14.

  ```text
  14  src/i18n/messages-en.ts      ← 가이드들이 출력 문구 몇 줄 때문에 카탈로그 전체를 핀
  12  src/project/plan.ts
  12  src/explain.ts
   9  src/commands/registry.ts
   7  package.json
  ```

- **재stamp 실태:** 커밋 173개 중 33개가 문서 해시 줄을 바꿨다. 문서별로 세면 297회이고, 그중 **131회(44%)는 본문이 한 줄도 바뀌지 않았다.** 예를 들어 `4d6e98b`에서 `docs/concepts/agent-loading.md`와 `docs/contributing/testing.md`는 해시 줄만 바뀌었다.
- **`파일:줄` 인용의 분포:** `implementation-mechanics.md` 223개, `implementation-principles.md` 109개, 나머지 26개 문서는 0~1개다. 이 두 문서는 재stamp할 때 거의 매번 본문도 함께 고쳐졌다. 헛걸림은 인용이 거의 없는 가이드·개요 문서에서 생긴다.
- **측정 방법:** 소스 하나당 실패 문서 수는 핀된 소스 파일마다 그 파일을, 또는 그 파일을 포함한 폴더를 핀한 문서 수를 센 값이다. 본문 무변경 재stamp는 git 기록에서 문서의 해시 줄이 바뀐 (커밋, 문서) 쌍마다 같은 커밋에서 그 문서의 다른 줄도 바뀌었는지 본 값이다.
- **실제 사고:** PR #54가 지침 항목을 열 개로 늘리면서 README의 해시 줄만 갱신했다. 본문은 "6개 항목"으로 남았고, 2026-09-18에 발견해 고쳤다.

## 문제 셋

```text
문서가 실제로 의존하는 것        문서가 핀한 것                     결과
─────────────────────────       ─────────────────────────────      ──────────────
출력 문구 3~4줄          ──▶    src/i18n/messages-en.ts 전체       문구 하나만 바뀌어도 14개 문서 실패
"모듈 구조" 요약          ──▶    src/ 아래 거의 모든 폴더           거의 모든 변경에 architecture.md 실패
논의 색인의 상태 몇 개     ──▶    논의 문서 폴더 전체                논의 문서 한 줄 수정에 README 실패
```

1. **핀이 너무 넓다.** 문서는 소스의 몇 줄에 기대는데 게이트는 파일이나 폴더 전체를 지켜본다.
2. **실패가 무엇을 읽어야 하는지 알려 주지 않는다.** 메시지는 핀한 소스 목록만 나열한다. 소스를 모두 합쳐 지문 하나를 만들기 때문에 어느 파일이 바뀌었는지 게이트도 모른다.
3. **승인이 한꺼번에 일어난다.** `--stamp`는 어긋난 문서를 모두 다시 기록한다. 한 문서만 읽고 실행해도 나머지가 함께 통과한다.

## 제안 동작

모델을 부르지 않고 diff와 파일 비교만으로 되는 것부터 한다.

1. **문서 단위 승인.** `--stamp`에 문서 경로를 받아 그 문서만 다시 기록한다. 경로 없이 실행하면 대상 목록을 보여 주고 멈춘다.
2. **실패 원인 표시.** 실패 메시지에 바뀐 소스 파일을 적는다. 소스별 지문을 따로 두거나, 마지막 stamp 이후의 변경을 git으로 찾아 보여 준다.
3. **해시 줄만 바뀐 문서 검출.** 커밋이나 PR에서 마커 두 줄 외에 아무것도 바뀌지 않은 문서를 찾아 이름을 출력한다. 판정은 diff만으로 하므로 평가로 고정할 수 있다. 문서 단위로 보기 때문에 PR #54처럼 다른 파일이 함께 바뀐 경우도 잡힌다.
4. **허브 핀 쪼개기.** 가이드가 메시지 카탈로그 전체를 핀하는 대신, 인용한 출력을 실제 실행과 대조하는 검사([`evals/doc-examples.test.ts`](../../../../evals/doc-examples.test.ts) 방식)로 옮긴다. `architecture.md`처럼 넓게 핀한 문서는 서술 범위를 좁히거나 핀을 나눈다.

## 검토한 대안

| 대안 | 내용 | 판단 |
| --- | --- | --- |
| 심볼 단위 앵커 | 문서를 함수·클래스에 묶고 정규화한 AST를 해시한다([fiberplane/drift](https://github.com/fiberplane/drift)의 방식, [외부 근거](../../../references.md#비교-대상)). | 채택하지 않는다. 위치 정보를 버리므로 줄 번호가 밀리는 변화를 놓친다. 이 저장소 문서는 `파일:줄` 인용이 규칙이라 그 변화가 중요하다. 파서 의존성도 생긴다. |
| 지문을 중앙 파일에 모으기 | 문서마다 마커를 두지 않고 저장소 루트의 잠금 파일에 모은다. | 채택하지 않는다. 지금은 문서 diff만 봐도 누가 무엇을 다시 승인했는지 보인다. 중앙 파일로 모으면 그 정보가 문서에서 사라진다. |
| 에이전트 리뷰 먼저 | [문서 정확성 자동 리뷰](doc-accuracy-review.md)를 먼저 도입한다. | 뒤로 미룬다. 그 제안은 지금 핀·승인 구조를 전제로 하고, 모델 호출 비용과 OIDC 설정이 필요하다. 위 3번이 같은 사례를 모델 없이 잡는다. |

## 결정

2026-09-19, 제품 소유자.

- **성공 기준:** 둘 다 하되 헛걸림부터 줄인다. 헛걸림이 많으면 사람이 문서를 읽지 않고 stamp만 하게 되므로, 원인을 먼저 줄여야 다시 읽기 검출도 제대로 작동한다.
- **구조:** 실행 대조와 절 단위 핀으로 바꾼다.
  - CLI 출력을 인용한 가이드와 README는 해시 대신 실제 실행 결과와 대조한다([`evals/doc-examples.test.ts`](../../../../evals/doc-examples.test.ts) 방식을 넓힌다). 그러면 메시지 카탈로그 전체를 핀할 이유가 없어진다.
  - 나머지 문서는 절(제목) 단위로 소스를 지정한다. 실패하면 바뀐 소스와 다시 읽을 절을 보여 준다.
  - `--stamp`는 문서나 절 단위로만 다시 기록한다.
  - `파일:줄` 인용 규칙은 유지한다. 심볼 단위 앵커는 [검토한 대안](#검토한-대안)대로 채택하지 않는다.
  - **2026-09-20 대체:** `파일:줄` 인용 규칙은 [문서가 코드를 인용하는 방식](code-citation-style.md#결정)의 결정으로 바뀌었다. 인용은 파일과 이름으로 하고 줄 번호를 쓰지 않는다. 심볼 단위 앵커를 채택하지 않는다는 판단은 그대로다.
- **구현 순서:** (1) 실행 대조로 옮길 문서를 옮기고 해당 핀을 없앤다. (2) 절 단위 핀, 문서·절 단위 `--stamp`, 실패 원인 표시를 넣는다. (3) 해시 줄만 바뀐 문서를 검출한다. (4) 두 지표를 다시 잰다. 본문 무변경 재stamp 비율은 커밋이 쌓여야 잴 수 있으므로, 그때까지는 검출이 실제로 잡은 건수를 구현 기록에 남긴다.
- **함께 고칠 것:** 게이트 계약의 정본인 [`doc-gate.md`](../../../contributing/doc-gate.md), `AGENTS.md`의 해시 게이트 요약, `repo-docs` 스킬 5단계, 게이트 평가. 마커 형식이 바뀌어 되돌리기 어려우므로 구현하는 변경에서 ADR을 쓴다.

## 비범위

- 문서 본문을 자동으로 고치지 않는다. 게이트는 다시 읽으라고 알릴 뿐이다.
- 게이트 대상 문서 목록 자체를 늘리거나 줄이지 않는다. 대상의 정본은 [문서 게이트](../../../contributing/doc-gate.md)다.

## 결정·검증 항목

- **성공 기준, 핀의 단위, `--stamp` 계약:** [결정](#결정) 절에서 정했다.
- **해시 줄만 바뀐 문서의 처리:** 경고로 둘지, `check`를 실패시킬지.
- **검증:** 개편 뒤 같은 방법으로 소스 하나당 실패 문서 수와 본문 무변경 재stamp 비율을 다시 잰다.

#### 구현 기록: 절 단위 핀

**2026-09-20.**

* **결정:** [결정](#결정)의 구조 가운데 절 단위 핀을 먼저 구현했다. 마커 형식은 그대로 두고, 한 문서에 마커를 여러 개 둘 수 있게 했다. 각 마커는 그 위치부터 다음 마커 전까지를 맡는다.
* **구현:** `tools/doc-sources.ts`의 `docSourceSections`가 문서에서 마커를 순서대로 읽고 각 마커 위의 제목을 함께 돌려준다. `tools/check-docs.ts`의 `checkDocSources`와 `--stamp`가 마커마다 검사하고 갱신한다. 실패 메시지는 `문서 (절 제목)` 형태다. 문서 전체를 하나로 보던 `docSourceSpec`은 지웠다.
* **평가:** `evals/doc-sections.test.ts` 3개가 마커 여러 개의 범위와 제목, 마커가 없는 문서, 해시 줄이 빠진 마커를 검사한다.
* **시범과 측정:** `docs/contributing/testing.md`의 핀 10개를 네 절로 나눴다. `.github/workflows/ci.yml`에 주석 한 줄을 넣자 전에는 이 문서 전체가 걸렸으나 이제 "CI 환경" 절만 걸린다. 다시 읽을 분량이 문서 40줄에서 그 절 6줄로 줄었다.
* **계획과 달라진 점:** 마커 문법을 새로 만들지 않았다. 기존 마커를 여러 번 둘 수 있게 하는 편이 문서와 도구 양쪽에서 변경이 작다.
* **인용을 커버리지로 인정:** `src` 아래 파일은 핀하거나 인용하면 덮인 것으로 본다(`tools/doc-sources.ts`의 `unpinnedSources`). 인용이 같은 지문을 같은 방식으로 지키므로, 핀을 절로 내리거나 없앨 때 커버리지 규칙에 걸리지 않는다.
* **개념 문서 네 개 이전:** `profiles.md`·`verification.md`·`managed-and-extension-areas.md`·`agent-loading.md`의 핀을 그 내용을 설명하는 절로 내렸다. 자동 이전도 시도했으나 배치가 절반만 맞아(예: 두 README가 서로를 핀하는 것을 엉뚱한 절로 옮김) 되돌리고 손으로 확인해 옮겼다. 남은 문서도 같은 방식으로 문서마다 판단한다.
* **현재 상태:** 문서 전체 핀만 가진 문서 22개, 절 단위로 나눈 문서 6개.
* **실행 대조 확대의 한계:** 명령 예시를 싣는 문서 10개를 실행 대조로 옮기려 했으나, 예시가 프로필 적용·충돌 같은 상태를 전제해 문서마다 시나리오 고정물이 필요하다. `verification.md`의 `verify --probe`는 실제 에이전트 CLI가 필요해 CI에서 재현할 수 없다. 그래서 절 단위 핀을 먼저 넓히고, 실행 대조는 고정물이 싼 문서부터 따로 붙인다.

#### 구현 기록: 승인 단위와 실패 원인, 지문만 찍은 문서 검출 (2026-09-21)

* **결정:** [결정](#결정)의 구현 순서 가운데 (2)의 남은 두 가지와 (3)을 구현했다. `--stamp`는 문서 경로를 받아 그 문서만 다시 기록하고, 실패 메시지는 핀 목록 대신 실제로 바뀐 소스를 지목하며, 지문만 다시 찍은 문서를 따로 찾아낸다. 마커 형식은 바꾸지 않았다.
* **구현:** `--stamp` 인자 해석은 `tools/doc-sources.ts`의 `stampTargets`가 하고, 경로가 없으면 `tools/check-docs.ts`의 `driftedDocuments`가 어긋난 문서 목록과 각각의 명령을 보여 준 뒤 1로 끝낸다. 전부 다시 기록하려면 `--stamp --all`을 쓴다. 바뀐 소스를 찾는 것은 `changedPinnedSources`이며, 그 지문을 기록한 커밋을 `git log -S`로 찾고 그 뒤의 변경과 커밋하지 않은 변경을 모아 `sourcesToReread`로 핀한 범위만 추린다. 지문만 찍은 문서는 `restampOnlyDocuments`가 diff만 보고 판정하고 `reportRestamped`가 출력한다.
* **평가:** `evals/doc-stamp-scope.test.ts` 12개다. 지문만 바뀐 문서, 문장까지 바뀐 문서(PR #54의 모양), 지문을 담은 소스 파일, 줄이 늘거나 준 문서, 인용 지문이 문장 안에 있는 경우, `--stamp`의 세 가지 인자 형태를 검사한다.
* **측정:** `tools/doc-sources.ts`를 고치자 문서 세 개가 걸렸고, 메시지가 핀 목록 대신 `tools/check-docs.ts, tools/doc-sources.ts`를 지목했다. 검출은 [측정](#측정) 절이 이름을 댄 커밋 `4d6e98b`으로 확인했다. `restampOnlyDocuments`가 그 커밋에서 문서 다섯 개를 찾았고, 측정 절이 적은 `docs/concepts/agent-loading.md`와 `docs/contributing/testing.md`가 모두 들어 있었다. 나머지 셋은 `docs/guides/apm-coexistence.md`, `docs/guides/team-sharing.md`, `docs/reference/exit-codes.md`다. `node tools/check-docs.ts --stamp docs/contributing/releasing.md`로 한 문서만 다시 기록하자 그 문서만 통과하고 나머지 둘은 그대로 실패했다. 경로 없이 `--stamp`를 실행하면 세 문서의 명령을 보여 주고 종료 코드 1로 끝난다.
* **계획과 달라진 점:** 소스별 지문을 마커에 따로 기록하는 안을 쓰지 않고 git으로 찾았다. 마커 형식을 바꾸면 28개 문서의 해시 줄을 한꺼번에 다시 찍어야 하는데, 그 커밋 자체가 이 주제가 없애려는 「본문 무변경 재stamp」의 가장 큰 사례가 되기 때문이다. 절 단위 `--stamp`는 넣지 않았다. 한 문서의 여러 절이 동시에 어긋나고 그중 한 절만 읽는 경우에만 쓸모가 있어서, 문서 단위를 먼저 쓰면서 실제로 필요한지 본다.
* **제약:** 실패 원인 표시는 git 저장소에서만 동작한다. 지문을 기록한 커밋을 찾지 못하면 지금까지처럼 핀 목록을 적는다. `--restamped`는 커밋된 변경만 보므로 작업 트리의 변경은 세지 않는다. 판정을 경고로 두었기 때문에 검사를 실패시키지는 않는다.
